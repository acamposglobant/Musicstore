MusicStore Code Review

Static analysis of the repository at commit 9f5f5c8 (branch main, 2026-11-25). Scope: all projects under src/, tests/, db/, the AppHost, CI workflow and solution file. Every finding below was verified against the source, the git history, or the Serilog log files produced by today's run.

Summary

The migration produced a clean, readable codebase: Clean Architecture layering is respected, SQL is parameterized everywhere, errors are RFC 9457 ProblemDetails with no leaked stack traces, and three test tiers exist. The problems found are mostly integration seams between well-built parts: a hosting call dropped in the last feature commit, an update handler that validates fields it never persists, a UI page reading fields an endpoint does not return, and a CI pipeline that cannot see one of the three test projects.

High severity

H1High

Catalog API no longer calls AddServiceDefaults()

src/MusicStore.Api/Program.cs:9-20
What
Commit b0b7678 (MIG-35, Serilog) replaced the line builder.AddServiceDefaults(); with the Serilog bootstrap. The new comment still says Serilog "coexists with the OTel exporter from ServiceDefaults", but that exporter is no longer registered. The Songs API, Gateway, Web and DbMigrations all still call it.
Impact
The catalog service exports no OpenTelemetry traces or metrics to the Aspire dashboard, has no "self" liveness check, and gets none of the HttpClient resilience and service-discovery defaults. The claimed Npgsql span instrumentation is wired but never exported. The /health endpoint still works only because the Npgsql integration registers its own health check.
Fix
Re-add builder.AddServiceDefaults(); before the Serilog call. Then see M2, because Serilog will otherwise discard the OTel log provider that this call registers.
H2High

Album update validates artist and genre but never saves them

src/MusicStore.Application/Albums/AlbumHandlers.cs:73-88, src/MusicStore.Infrastructure/Repositories/AlbumRepository.cs:70-74
What
UpdateAlbumHandler looks up request.ArtistId and request.GenreId (two extra queries) and throws 422 if either is missing, then calls only album.UpdateTitle(...). The repository runs UPDATE album SET title = @title. Album has no method to reassign its artist or genre.
Impact
The Albums page edit form lets the user pick a different artist or genre and reports success, but the change is silently discarded. The integration test passes because it sends the same ids back; the unit test asserts only the title.
Fix
Add Album.Reassign(int artistId, int genreId) (or fold it into an Update method), call it from the handler, and extend the SQL to SET artist_id = @artistId, genre_id = @genreId, title = @title. Add a unit test asserting the new ids and an integration test that changes them.
H3High

Domain guard exceptions surface as HTTP 500 instead of 422

src/MusicStore.ServiceDefaults/ErrorHandling/MusicStoreExceptionHandler.cs:28-33, all Create/Update handlers
What
Entities validate input with ArgumentException and ArgumentOutOfRangeException. The exception handler maps only NotFoundException and ValidationException; everything else becomes 500 "An unexpected error occurred" and is logged as an error. Only CreateArtistHandler (blank name) and CreateSongHandler (non-positive duration) pre-validate.
Impact
These client mistakes return 500 even though every endpoint advertises 422 via ProducesProblem: blank genre name or description, album title or artist name over 100 characters, song name over 50 characters, blank name on any PUT, non-positive duration on PUT /songs. The UI then shows the generic error text and the ops log fills with false alarms.
Fix
Either validate request records up front in one place (a small validator per request, or DataAnnotations plus an endpoint filter) and throw ValidationException, or have the handlers catch ArgumentException from entity construction and rethrow as ValidationException. Keep the domain guards as the last line of defense. Add integration tests for the over-length and blank cases.
H4High

Album detail page reads artist and genre names from an endpoint that does not return them

src/MusicStore.Web/Services/CatalogApiClient.cs:56, src/MusicStore.Web/CatalogModels.cs:12, src/MusicStore.Web/Components/Pages/AlbumDetail.razor:30-32
What
The Web project has a single AlbumDto with non-nullable ArtistName and GenreName. GetAlbumAsync calls GET /catalog/albums/{id}, which returns the flat API DTO (id, artistId, genreId, title). Deserialization leaves both names null despite the non-nullable annotations.
Impact
The album detail header renders as "by · Genre: " with empty values on every album. The UI smoke test only asserts the route returns 200.
Fix
Add GET /albums/{id}/with-details to the catalog API (the multi-mapping query already exists for the list) and use it from the detail page, or split the Web DTOs into AlbumDto and AlbumDetailsDto matching the API so the compiler flags the mismatch.
H5High

Integration tests are not in the solution, so CI never builds or runs them

MusicStore.slnx:14-17, .github/workflows/ci.yml:30-33
What
The solution's /tests/ folder lists only Application.UnitTests and Infrastructure.Tests. CI runs dotnet build and dotnet test against MusicStore.slnx, so MusicStore.IntegrationTests (30 tests, the only coverage of the gateway, YARP routing, ProblemDetails over HTTP and the UI) is never compiled on CI. The README states all three suites run.
Impact
End-to-end regressions (for example H2 or a broken gateway route) pass CI. The project can also stop compiling without anyone noticing.
Fix
Add the project to MusicStore.slnx. CI's ubuntu-latest runner has Docker, which Aspire testing needs; if the run time is a concern, gate it to pull requests only or run it as a separate job.

Medium severity

M1Medium

Request-completion log lines have an empty correlation id

src/MusicStore.Api/Program.cs:54-65, src/MusicStore.Songs.Api/Program.cs:55-66
What
app.UseSerilogRequestLogging() is registered before the middleware that pushes CorrelationId into LogContext. Serilog writes its completion line after the downstream pipeline returns, by which point the pushed property has been disposed.
Evidence
In today's src/MusicStore.Api/logs file, 91 of 404 lines (every "HTTP ... responded" line) end in (correlation: ), while handler and repository lines carry the id. The Songs API log shows the same pattern (32 lines).
Fix
Register the correlation middleware before UseSerilogRequestLogging(), or set the property through options.EnrichDiagnosticContext so the completion event carries it regardless of order.
M2Medium

UseSerilog discards the OpenTelemetry log provider

src/MusicStore.Songs.Api/Program.cs:18-22 (and the catalog API once H1 is fixed)
What
AddServiceDefaults() registers builder.Logging.AddOpenTelemetry(...) so logs reach the Aspire dashboard. UseSerilog(...) with the default writeToProviders: false replaces the logger factory and ignores the other providers.
Impact
The dashboard's Structured Logs view shows nothing from the APIs; only console and files receive logs. The MIG-35 commit message describes coexistence that does not happen.
Fix
Pass writeToProviders: true, or add Serilog.Sinks.OpenTelemetry and point it at OTEL_EXPORTER_OTLP_ENDPOINT.
M3Medium

APIs start before the database migrations have run

src/MusicStore.AppHost/AppHost.cs:9-24
What
The migrations resource applies the schema and seed, but catalog and songs only .WaitFor(database). Nothing waits for the migration run to complete. The Npgsql health check only verifies connectivity, so the gateway reports both APIs healthy while the tables may not exist yet.
Impact
On a fresh volume the first requests can fail with "relation album does not exist" until DbUp finishes. The integration fixture is exposed to the same race.
Fix
Hold a reference to the migrations resource and add .WaitForCompletion(migrations) to both APIs.
M4Medium

Least-privilege songs role is never used and its password is committed

db/300_songs_role.sql:9, src/MusicStore.AppHost/AppHost.cs:21-24, src/MusicStore.Songs.Api/Program.cs:26
What
The script creates musicstore_songs with the literal password musicstore_songs. The AppHost hands the Songs API the same owner connection string as the catalog (WithReference(database)), and the Program.cs comment claims the service connects with the restricted role.
Impact
A security control that exists on paper but not in practice, plus a plaintext credential in version control that will be flagged by any secret scanner.
Fix
Either wire the role for real (an AppHost parameter for the password, a connection string built from it, and the GRANTs kept) or delete the script and the comment. Do not keep both states.
M5Medium

Repositories throw KeyNotFoundException, which maps to 500

src/MusicStore.Infrastructure/Repositories/*.cs, every UpdateAsync and DeleteAsync
What
When zero rows are affected the repositories throw the BCL KeyNotFoundException. The handler loads the entity first, so this only happens if the row disappears between the read and the write, but when it does the exception handler returns 500 rather than 404.
Fix
Throw the Application layer's NotFoundException (Infrastructure already references Application), or return the affected count and let the handler decide.
M6Medium

Dapper calls ignore the cancellation token

all four repositories
What
The token is passed to OpenConnectionAsync only. The query calls use the string overloads, which take no token. A client disconnect or a resilience timeout cannot cancel the running statement.
Fix
Wrap each call in new CommandDefinition(sql, parameters, cancellationToken: cancellationToken).
M7Medium

Unit of work is registered, tested, and unusable

src/MusicStore.Infrastructure/UnitOfWork/NpgsqlUnitOfWork.cs, src/MusicStore.Application/Interfaces/IUnitOfWork.cs, DependencyInjection.cs:38
What
No handler injects IUnitOfWork. More importantly, every repository opens its own connection from the data source, so even if a handler began a transaction the repository calls could not enlist in it. The abstraction promises a transaction boundary that the rest of the design cannot honor.
Fix
Decide: either make repositories accept a connection/transaction (or resolve one from the scoped unit of work) and use it where multi-step writes exist, or delete the unit of work and its six tests. Today it is dead code with a misleading contract.
M8Medium

Blazor pages load their data twice per navigation

src/MusicStore.Web/Components/App.razor:14, every page's OnInitializedAsync
What
Routes uses InteractiveServer with prerendering enabled (the default). OnInitializedAsync therefore runs once during server prerender and again when the circuit connects, so each visit to Albums issues six gateway calls instead of three.
Fix
Persist the prerendered state with PersistentComponentState (or the [PersistentState] attribute already used in Error.razor), or disable prerendering with new InteractiveServerRenderMode(prerender: false).
M9Medium

Repository tests start one PostgreSQL container per test class

tests/MusicStore.Infrastructure.Tests/PostgresFixture.cs, five test classes using IClassFixture<PostgresFixture>
What
The fixture's comment says "one container, many databases", but IClassFixture creates a fixture (and container) per class. Five containers start in sequence; the "own database per class" isolation it describes is not implemented either (all classes run against the default database).
Fix
Use a collection fixture (as the integration tests already do) and, if isolation matters, create a database per class from the shared container.
M10Medium

Public songs URL is /songs/songs/...

src/MusicStore.Gateway/appsettings.json:20-26, src/MusicStore.Songs.Api/Endpoints/SongEndpoints.cs:18
What
The gateway strips the /songs prefix and the Songs API then maps its group at /songs, so clients call /songs/songs?albumId=1 and /songs/songs/{id}. The README describes the route as /songs/** → songs API, which hides the doubled segment. The catalog side (/catalog/artists) does not have this problem.
Fix
Map the Songs API group at the root, or keep the prefix in the gateway and drop the PathRemovePrefix transform. Update the Web client, the integration tests and the README together.

Low severity and smells

L1Low

Hosting code is copy-pasted between the two APIs

src/MusicStore.Api/Program.cs, src/MusicStore.Songs.Api/Program.cs

The Serilog bootstrap, correlation middleware, HttpLogging options, Scalar/OpenAPI mapping and root endpoint are identical in both files, and the two appsettings.json Serilog sections differ only by file name. H1 is the kind of drift this invites. Move them into ServiceDefaults as AddMusicStoreLogging() / UseMusicStoreRequestPipeline().

L2Low

Every request is logged three times

ASP.NET Core HttpLogging (request and response headers), Serilog request logging, and OpenTelemetry ASP.NET Core instrumentation all run on each request. Pick one text log of requests; keep OTel for traces.

L3Low

Namespaces do not match their projects

src/MusicStore.Songs.Api/Endpoints/SongEndpoints.cs:1, src/MusicStore.ServiceDefaults/ErrorHandling/*.cs:1

The Songs API endpoints live in MusicStore.Api.Endpoints, and the ServiceDefaults error handling in MusicStore.Api.ErrorHandling. Both are leftovers from the MIG-21 extraction.

L4Low

Layering: ServiceDefaults depends on the Application layer

src/MusicStore.ServiceDefaults/MusicStore.ServiceDefaults.csproj:13, src/MusicStore.AppHost/MusicStore.AppHost.csproj:17-18

The shared hosting project references Application so the exception handler can see NotFoundException. That drags the Application layer into the Gateway and Web, which do not need it. A small marker interface (for example IHttpStatusException) in ServiceDefaults, implemented by the Application exceptions, would invert the dependency. The AppHost also references MusicStore.Api and ServiceDefaults while using path-based AddDotnetProject, so those references do nothing.

L5Low

Domain navigation collections are never populated

src/MusicStore.Domain/Album.cs, Artist.cs, Genre.cs, Song.cs

Artist.Albums, Genre.Albums and Album.Songs are always empty because Dapper never fills them, and the constructors that wire them (Album(Artist, Genre, string), Song(Album, string, TimeSpan)) are unused outside the Domain project. Album has five constructors, including (int, int, string) next to (int, int, int, string), which is easy to call with the arguments shifted. Remove the collections and entity-wiring constructors, or load them for real.

L6Low

Guard logic repeated across entities

SetName, SetTitle, SetDescription each repeat the same null/whitespace and max-length check with a different message. A single Guard.Text(value, max, paramName) helper removes five copies.

L7Low

Global Dapper setting mutated during DI registration

src/MusicStore.Infrastructure/DependencyInjection.cs:29

DefaultTypeMap.MatchNamesWithUnderscores = true is process-wide static state set from an extension method. Every query already aliases its columns, so the setting is also redundant. Remove it, or set it once in a module initializer with a comment.

L8Low

Unbounded list endpoints

GET /artists, /genres, /albums, /albums/with-details, /songs return every row with no paging or limit. Fine for the seed data, not for a real catalog.

L9Low

Foreign keys verified with extra queries instead of the database

CreateAlbumHandler, UpdateAlbumHandler, CreateSongHandler

Creating an album costs three round trips and still has a window where the artist can be deleted between check and insert. Catching Npgsql's 23503 (foreign key violation) and mapping it to 422 is one round trip and race-free.

L10Low

Song duration display and parsing edge cases

src/MusicStore.Web/Components/Pages/AlbumDetail.razor:58,146,167, src/MusicStore.Songs.Api/Endpoints/SongEndpoints.cs:10
  • The table formats with mm\:ss, so a 1:14:30 track displays as 14:30.
  • TimeSpan.TryParse("3:30") yields three hours thirty minutes; the label says hh:mm:ss but users will type m:ss.
  • The endpoint comment says duration is serialized as an ISO-8601 duration; System.Text.Json uses the constant c format (hh:mm:ss).
L11Low

Page cancellation token never cancelled; timeouts crash the circuit

all four data pages, LoadAsync / Dispose

loadCts is disposed but never cancelled, so in-flight requests continue after navigation. The catch blocks handle only CatalogApiException and HttpRequestException; a TaskCanceledException from the resilience handler's timeout escapes and shows the "An unhandled error has occurred" banner. Add catch (OperationCanceledException) and cancel in Dispose.

L12Low

Deletes have no confirmation

Deleting an artist cascades to its albums and their songs (ON DELETE CASCADE) with a single click and no confirmation step.

L13Low

HTTPS redirection with an HTTP-only endpoint

src/MusicStore.Web/Program.cs:34, src/MusicStore.AppHost/AppHost.cs:40

The AppHost gives web only WithHttpEndpoint(), but Program.cs keeps UseHttpsRedirection(). ASP.NET Core logs "Failed to determine the https port for redirect" on every request (visible in the .coda/tmp web logs). Drop the call or add an HTTPS endpoint.

L14Low

Health endpoints exist only in Development

src/MusicStore.ServiceDefaults/Extensions.cs:107-121

The Aspire template default maps /health and /alive only when IsDevelopment(). Outside Development the gateway's downstream probes get 404 and report Degraded, and orchestrators have no readiness probe. Decide deliberately: map them always with a port or auth restriction, or document that production readiness is handled elsewhere.

L15Low

Package version drift and repeated project properties

Aspire.Npgsql 9.5.2 sits next to Aspire.Hosting 17.0.0; the three test projects use xunit 2.9.3, xunit.v3 3.1.0 and Microsoft.NET.Test.Sdk 18.0.0 / 17.14.1 / 17.12.0. TargetFramework, Nullable and ImplicitUsings are repeated in every csproj although Directory.Build.props already sets them. Adopt Central Package Management (Directory.Packages.props) and delete the repeated properties.

L16Low

DbMigrations builds a host it never runs

src/MusicStore.DbMigrations/Program.cs:6-15

Host.CreateApplicationBuilder is used only to read configuration; AddServiceDefaults() registers OpenTelemetry and health checks into a host that is never built, so the migration run emits no telemetry. Either build and run the host (DbUp inside an IHostedService) or drop the ServiceDefaults call and read configuration directly.

L17Low

Comment and documentation drift

  • db/100_seed.sql header says 3 artists and 3 genres; it inserts 4 of each.
  • src/MusicStore.AppHost/AppHost.cs:26-33 contains the same four-line comment twice.
  • The catalog Program.cs describes an OTel exporter that is not registered (H1); the Songs Program.cs describes a database role that is not used (M4).
  • 404 responses are logged at Warning with the full exception, so every miss writes a stack trace. Log the message only, or at Information.
  • No authentication, authorization or rate limiting exists on the gateway or the APIs. The legacy service had none either, but it should be a recorded decision rather than an omission.

What is in good shape

  • Good Parameterized SQL everywhere; no string concatenation into queries anywhere in the four repositories.
  • Good RFC 9457 ProblemDetails with distinct 404/422 mapping and no exception details on 500s, fixing the legacy includeExceptionDetailInFaults leak.
  • Good Domain invariants enforced in constructors with private setters; DTOs are records; handlers are small, sealed and stateless.
  • Good TreatWarningsAsErrors and EnforceCodeStyleInBuild on for every project; CI builds in Release with zero warnings.
  • Good Vulnerable transitive packages pinned with the advisory id noted in the csproj comment.
  • Good Schema parity script (db/200) asserts types, FK rules, nullability and indexes against the legacy model, and runs under DbUp's journal.
  • Good Repository tests run against the real DDL in a PostgreSQL container; integration tests boot the whole Aspire graph and go through the gateway.
  • Good Build output, IDE state, logs and local Aspire state are all gitignored; the tree is clean.

Suggested fix order

  1. H1 and M2 together: restore AddServiceDefaults() in the catalog API and let Serilog write to providers. One small PR, immediate observability win.
  2. H5: add the integration tests to the solution so the remaining fixes are protected by CI.
  3. H2 and H4: the two user-visible data bugs (album reassignment and empty detail header), each with a new integration test.
  4. H3 plus M5: one validation pass so every client error is a 422 and every missing row a 404.
  5. M1, M3, M4: logging order, migration wait, and a decision on the songs role.
  6. L1 and M10 when touching the APIs next: consolidate hosting code into ServiceDefaults and fix the songs URL shape.
  7. The remaining Medium and Low items as routine cleanup.

Method: full read of every C#, Razor, SQL, csproj, JSON config and workflow file in the repository; cross-checks with git log -S for the regressions, and with the Serilog output in src/*/logs for the correlation-id finding. No code was changed.
